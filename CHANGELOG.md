# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **The Architecture picture rounds its coordinates to two decimals:** the legend positions no longer carry floating-point noise such as 399.9999999999999, so `make_architecture.py --check` gives the same answer on every machine; the shared tool is the one of ARMOR-COMMON.
- **The shared tools of the manifest and the status lights gain an opt-in strict check of the evidence:** `sync_manifests.py` and `status_lights.py` take `--strict-evidence` (off by default; `ARMOR_STRICT_EVIDENCE=1` switches it on for `armor_ci_validate.py`).
- The watch contract lists a `bindSender` setting (off by default, Wear OS only); the Wear OS app now offers it as a button that keeps the phone that switched the alerts on as the only sender listened to, with its texts in eight languages. The Apple Watch has one paired iPhone and no sender to tell apart.

- **The watch can listen to one phone only:** `WatchSession.bindSender` (off by default, as always) keeps the node that switched the alerts on as the only sender whose alerts are taken until they are switched off, so another node of the Data Layer cannot raise or clear alerts; the service of the Data Layer now hands over the sender of each message.

- **The watch sends the confirmation to the phone app that declares itself, not to any connected device:** the watch app declares a capability and looks for the capability of the phone app among the reachable nodes, and falls back to the connected nodes only when no node declares it. The identifier of the app is not changed. The note on how a message reaches the other side is in the protocol document; it has not been run on a real watch.

- **The whole conversation between phone and watch runs in memory, with faults on purpose:** `Simulation.kt` adds a simulated link (out of range, a message lost on the way, a duplicate, a burst held up and let go in the wrong order), the sending side of the two phone apps (the switch, the alerts, the clear, and a confirmation acted on only for an alert it sent, once, before it expires and only while the option is on) and a simulated server that acknowledges an alarm once; `SimulatedPair` wires them on a clock the test moves and can restart the watch. 14 scenarios in Kotlin (`SimulatedPairTest`) and the same 14 in Python (`tests/test_watch_simulation.py`, `tools/watch_simulation.py`) with every message checked against the contract, and a test that keeps the two sets in step. The manifest says `evidence: simulator`; the Data Layer, WatchConnectivity, the pairing and the screens on a real watch stay to be tried (see `docs/PROTOCOL.md`).
- **The Wear OS app has a release build that is signed outside GitHub:** the release build type of `wear/` has no signing configuration and no list of dependencies in the APK, and the new manual workflow `apk-build.yml` compiles it twice from the commit the run starts from (Gradle, JDK 21, `-ParmorWear`), aligns it, compares the two builds byte by byte, refuses any signature or key, attests the files and uploads them as the artifact `apk-watch-<version>` (a dry run by default; with it off a draft release waits for the approval of the owner). The signed APK is named `ARMOR-WATCH-release.apk`; the way it is built, signed and named is written in `docs/PROTOCOL.md`, and three tests read the workflow and the build file as text (manual, unsigned, built twice, attested, actions pinned by commit, no secrets). Nothing has run on a watch.

## [0.0.2] - The Wear OS app, the Apple Watch app and the watch end of the conversation

- **The Apple Watch app is built inside the iPhone project:** ARMOR-IOS-CONTROL describes the app of `watchos/` as a target of its own Xcode project (companion `es.electrohobby3d.armor.ios`, embedded in the iPhone app, same version and build number) and takes the sources and the Swift core from this repository, so the watch app has one source only. The macOS workflow of ARMOR-IOS-CONTROL builds the iPhone app with the watch inside and the watch app on its own for the watchOS simulator (both pass in GitHub Actions); `watchos-build.yml` keeps building the watch app alone. Nothing changes in the messages or in the rules (off until the iPhone says so, nothing written to the watch, no login, no keys). Evidence: simulator; the pairing with a real iPhone and a real watch is still to be tried.
- **The manifest and the architecture picture speak of the Apple Watch app too:** the notes of `armor.project.json` and the description of `docs/architecture.json` (and its picture) name `watchos/` and the sender of ARMOR-IOS-CONTROL, and no longer say that the iPhone has no counterpart.
- **The Apple Watch app:** `watchos/` holds a Swift package (`ArmorWatchCore`: the messages and their checks, the inbox, the session and the runtime, written from the same contract as the Kotlin core and tested with the same accepted and rejected examples of `docs/watch_alert_contract.json`, 18 tests) and a SwiftUI app (`App/`: the screen, WatchConnectivity and the words in the eight languages) described for XcodeGen (`project.yml`). It follows the family: the rules live in a package with no UI, the app target holds only the screen and what needs the device, and the project is made by XcodeGen and built only on a Mac. Off until the iPhone says otherwise, nothing is written to the watch, no login and no keys; a message that was not delivered live is not queued. The manual workflow `watchos-build.yml` (macOS) runs `swift test` and builds the app for the watchOS simulator (both passed in GitHub Actions). Evidence: simulator; it has never run on a watch or on a Mac of the owner. The sender is in ARMOR-IOS-CONTROL.
- **The manifest and the architecture picture say what exists:** the notes of `armor.project.json`, the description and the screen box of `docs/architecture.json` and its picture no longer say that the Wear OS screen and the Data Layer service are not written: the app is in `wear/` (compiled and unit-tested in GitHub Actions, never run on a watch), the sender is in ARMOR-ANDROID-CONTROL (off by default) and an iPhone has no counterpart because it does not pair with a Wear OS watch.
- **The Wear OS app:** `wear/` is a Compose for Wear OS screen that draws what `WatchSession` says (the alerts, the most serious first, each with a Confirm button until it is confirmed, and a word when the phone is out of reach), the service of the Data Layer that takes the messages of the phone on `/armor/alert` (nothing else) and sends the confirmation back on `/armor/alert/ack`, and a runtime that shares one session between them behind a lock. It has no login, no network of its own and writes nothing to storage; the words are in the eight languages. It is part of the build only with `-ParmorWear` (it needs the Android SDK), and the manual workflow `wear-build.yml` builds it, runs its tests and those of the core and keeps the debug APK for a week. It compiles and passes its tests in GitHub Actions; it has never run on a watch, and the sending side in the phone apps is still to do.
- **The watch end of the conversation, tried against a phone that exists only in memory:** `WatchSession` takes the texts of the phone (only on the path of the alerts, only what the contract allows), keeps the alerts in memory and gives the screen a `WatchScreen` to draw (off, quiet or the alerts, most serious first, each with whether it can be confirmed or already was); `confirm` hands the acknowledgement to the phone once and, when the phone cannot be reached, leaves the button to press again. `SimulatedPhone` records what the watch sends and can be made unreachable. Evidence: simulator; the Wear OS screen and the Data Layer service are still not written.

## [0.0.1] - The message contract between the phone and the watch, and the Kotlin core that reads it

- **The message contract between the phone and the watch:** `docs/watch_alert_contract.json` names the four messages (the switch of the relay, an alert, the clear of an alert and the confirmation the watch sends back), their limits and accepted and rejected examples, and `tools/watch_contract.py` runs them in Python. Everything is off until the phone says the option of the watch is on.
- **The Kotlin core of the watch:** `WatchProtocol` reads and checks every message without ever throwing, and `AlertInbox` keeps the alerts in memory only (most serious first, a limit of eight, an alert that expires disappears, the confirmation goes out once), starting switched off. The tests run the same examples as the contract and the rules of the inbox.
- **The repository and its checks:** manifest, licence, security policy, eight-language README, pictures and the CI baseline of the family.
